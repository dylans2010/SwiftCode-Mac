# MIGRATION_FEATURE_PARITY.md — SwiftCode zero-feature-loss migration ledger
## 0. Mission, bases, and authority
**Mission:** port 100% of the functionality of the original SwiftCode application into SwiftCode-New (Ycode), so the resulting application retains every original feature, capability, tool, workflow, and integration, presented through SwiftCode-New's existing UI and architecture. Zero feature loss. Zero placeholders. Zero silent omissions. The audits and this ledger are Phase 1–2 scoping only — they are NOT the deliverable. Implementation continues ledger-by-ledger until every entry is `VERIFIED`.
- **Source (original functionality):** SwiftCode-Mac, `https://github.com/dylans2010/SwiftCode-Mac`, branch `main` @ `d51a8f0d` (v1.1.0, build 2), 2,231 Swift files / 1,288,617 lines under `SwiftCode/` (~383k hand-written; `SDK/Distribution/` is 905k generated).
- **Destination (UI / architecture patterns):** SwiftCode-New (Ycode), `https://github.com/dylans2010/SwiftCode-New`, branch `feature/swiftcode-parity-migration` from `main` @ `22f2c27` (1.0.0-beta.2), 2,172 Swift files. SwiftPM-only — no `.xcodeproj` for Ycode itself, so migrated code must become `ycode/Package.swift` targets.
- **Method:** source-read only. Both audits were produced by reading source, `rg`/`grep` searches, and file listings. Nothing was built, executed, or run on macOS here (Linux environment, no Xcode toolchain), so every status below is source-level. Mac build, test, and live verification remain pending on Dylan's Mac and must be recorded as evidence before any entry is marked `VERIFIED`.
- **Sources for this ledger:** `~/workspace/swiftcode-parity-migration/audit/swiftcode-mac-inventory.md` (PARTIAL checkpoint, 948 lines) and `~/workspace/swiftcode-parity-migration/audit/swiftcode-new-architecture.md` (546 lines).
### MIT authorisation (recorded)
Dylan confirmed on 2026-11-05 that SwiftCode-Mac code is his to port under MIT. SwiftCode-Mac has **no `LICENSE` file and no licence statement in its README**; Ycode contributions are MIT. This recorded confirmation is the basis for direct porting in this migration.
### Clean-room note
SwiftCode-New's `AGENTS.md` mandates a clean-room protocol: dirty-room analysis only in `research/dirty/` (git-ignored), specs in `specs/`, implementation only in `ycode/` / `frameworks/` / `composer/` reading specs + public docs / suitably licensed open source. Spec-first (audit → behaviour specs in `specs/ide/` → implement from specs) is the protocol-pure default. Direct porting of SwiftCode-Mac code is authorised by Dylan (see MIT authorisation above) and is used where it costs nothing to do so; ported code lives only in clean-room dirs (new `Ycode*` targets / `frameworks/` packages), never in `specs/` or `research/`.
### How to read this ledger
- **Destination location / Integration columns are PROPOSED**, derived from the SwiftCode-New audit's integration seams (§6) and mapping table (§7). Nothing in those columns is implemented yet — every row starts `NOT STARTED`.
- **Original location / behavior** are taken verbatim from the Mac inventory (its §7 seed and §2.2 tool table). Where the Mac inventory is PARTIAL, the row says so instead of inventing detail.
- If a feature is discovered during implementation, add it here immediately and split it into separate entries if it contains subfeatures. This ledger is the living source of truth until final verification.
## 1. Status definitions
| Status | Meaning |
|---|---|
| `NOT STARTED` | No implementation work has begun. |
| `IN PROGRESS` | Implementation is under way; not yet functionally complete. |
| `IMPLEMENTED` | Code exists and compiles in the destination; **not** complete — functional verification is still required. |
| `VERIFIED` | Functional parity demonstrated with recorded evidence (test / build / live run on macOS as applicable). **Only `VERIFIED` counts as complete.** |
| `BLOCKED` | A genuine external dependency blocks progress; the exact blocker is recorded in the row. |

A screen compiling does not mean complete. A button appearing does not mean complete. A feature being partially functional does not mean complete.
